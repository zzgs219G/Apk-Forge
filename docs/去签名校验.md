# 去签名校验模块

> 本文只讲「去签名校验」这一个功能，与 `流程文档.md`（dex 注入）是**并列的两条线**，
> 不要混读。两条线的共同点只有一个：都产出一个未签名 APK。

---

## 0. 一句话

把「让别的 App 认为自己的签名还是原版」这件事，做成手机上点一下就能完成的流程。

产物**未签名**，自己用 keystore 签。

---

## 1. 与 dex 注入的区别（先分清，否则看错文档）

| | dex 注入（`流程文档.md`） | 去签名校验（本文） |
|---|---|---|
| 目的 | 往别人包里塞**我们自己的代码**（弹窗等） | 让别人的**签名校验失效** |
| 改什么 | 目标类的方法体（插 `invoke-static`） | `AndroidManifest.xml` 的 `android:name` + 新增 dex/assets |
| 入口 | 复制现有的 `classes.dex` 后改指令 | 不动任何原有 dex |
| 载荷 | `PayloadDialog.dex`（预编译） | `boot.dex` + `payload.dex`（远端下载） |
| 签名 | 产物未签名 | 产物未签名 |

**一句话记忆**：dex 注入改「行为」，去校验改「环境」。

---

## 2. 原理：改「系统返回值」，不改 App 代码

App 无论怎么写校验，最终必须从某个信息源取签名：

```
目标 App: "PackageManager，我的签名是什么？"
              ↓
我们的拦截: "是 <原版证书>"        ← 在这里撒谎
              ↓
目标 App: 算哈希 → 与原版一致 → 判定通过
```

因为不改 App 的任何代码，**它用什么方式写校验、混淆成什么样都不影响**。
这是「通用」的来源 —— 一旦要去找校验点在哪，就退化成逐包手工分析了。

### 三层拦截（实测都能工作）

| 层 | 手段 | 稳定性 |
|---|---|---|
| ① 替换 `PackageInfo.CREATOR` | 包一个自定义 `Parcelable.Creator`，反序列化后改结果 | 最稳（public 字段，十年没变） |
| ② 代理 `ActivityThread.sPackageManager` | `Proxy` 包 `IPackageManager` 接口 | 中（依赖内部字段，但按类型找） |
| ③ 改 `signingInfo` 内部数组 | `getApkContentsSigners()` 返回内部数组引用，原地改元素 | 最稳（不碰 hidden 字段） |

**三层叠加**，任一层失效还有另外两层兜住。

## 3. 挂载点：`android:name`（为什么必须是最早）

```
ContentProvider.onCreate       最早
Application.attachBaseContext  ← 我们挂这里（SigFixApp）
Application.onCreate
Activity.onCreate              ← 只挂这里会漏掉上面三种
```

目标 App 可能在任何一层校验。挂 Activity 会漏，所以改 Manifest 指向 `SigFixApp`。

### 代理链，不是替换

`SigFixApp` 不「取代」原 Application，而是**代理**它：

```
系统实例化 SigFixApp
    ↓
attachBaseContext(ctx)
    ① 装 hook（早于原 Application 初始化）
    ② 读 assets/nc_sigfix/sigfix.json（证书 + 原类名）
    ③ 反射创建原 Application（无参构造 + Application.attach）
    ④ 清零它的 mBase，再调它自己的 attachBaseContext
    ⑤ 替换 ActivityThread.mInitialApplication = 原实例
    ↓
onCreate()
    └─ 转发给原 Application.onCreate()
```

**为什么不学 MT 改父类**：MT 把原类的 `extends Application` 换成
`extends KillerApplication`，Manifest 不动。缺点是原类若继承
`TinkerApplication` / `MultiDexApplication`，换父类等于删掉那些逻辑，
App 起不来。代理链保住了原继承关系与全部初始化逻辑。

## 4. 处理一个 APK 的九个步骤

```
① 读输入
   ├─ 从 Signing Block 提原证书 DER（CertExtractor，纯 Java 解析）
   ├─ 读二进制 AndroidManifest（包名 / 原 Application / LAUNCHER）
   └─ 列出已有 classes*.dex

② 取载荷（PayloadFetcher：缓存优先，下载兜底，sha256 校验）
   └─ boot.dex / payload.dex / libusign_arm64.so / libusign_armv7.so

③ 提原签名块（v2/v3 原始字节，后面要搬进中间包）

④ 决定新 dex 名
   └─ classes{最大序号+1}.dex，绝不占已有名字

⑤ 改写 Manifest（两处，都不许解码成文本）
   ├─ android:name → com.nc.uncheck.SigFixApp
   └─ extractNativeLibs → true（不存在则新增）

⑥ 建中间包
   ├─ 原包逐条复制（保留压缩方式）
   ├─ 替换 AndroidManifest.xml
   └─ 追加 6 个条目：
         classes{N+1}.dex        ← boot.dex
         assets/nc_sigfix/payload.dex
         assets/nc_sigfix/sigfix.json   ← 证书 + 原 Application 类名
         lib/arm64-v8a/libusign.so      ← STORED
         lib/armeabi-v7a/libusign.so    ← STORED

⑦ 注入签名块   ← 必须在 ⑥ 之后（ZipOutputStream 重写会丢掉它）

⑧ 数据复用     ← 必须在 ⑦ 之后（origin.apk 的数据区 = 中间包全字节）
   └─ 新增 assets/nc_sigfix/origin.apk，与整包共享物理字节

⑨ 自检 → 输出未签名 APK
   ├─ 七个落点齐全
   ├─ Manifest 回读确认 android:name 与 extractNativeLibs
   ├─ 新 dex magic 合法 / .so 是 STORED
   ├─ 复用结构（origin.apk 是完整 APK、resources.arsc 4 字节对齐）
   └─ 原包有签名块时，origin.apk 里也必须带
```

耗时约 2~4 秒（22MB 包），全程本地，不联网（载荷已缓存时）。

> ⚠️ **⑦⑧ 的顺序是硬要求**。云端 2026-11-24 因为签名块没保留，
> 加固包的 `.ncx` 段解密出乱码 → 跳野地址 → SIGBUS。
> `UncheckPipeline` 的自检与 `UncheckPipelineTest` 都钉住了这条。

## 5. 载荷为什么分两个 dex

```
boot.dex      SigFix + SigFixApp   → 进目标 App 的 classes{N+1}.dex
payload.dex   SigFixImpl            → 进 assets，运行时由 DexFile 加载
```

**关键**：`SigFixImpl` 必须由 **BootClassLoader** 加载，才能反射访问 hidden API。

```
new DexFile(path)     ← 不传 ClassLoader
      ↓
ART 用 BootClassLoader 加载 payload.dex
      ↓
其中的类被视为「系统域」
      ↓
反射 ActivityThread 等 hidden API 不被拦截
```

如果把它编进 App 自己的 dex，它就是应用域，反射照样被拦（实测 Android 17：
`setHiddenApiExemptions` 直接 `blocked`，报 `NoSuchMethodException`）。

### native hook 分三档（2026-11-27 上游新增）

`sigfix.json` 多了一个 `hookLevel` 字段，控制 native 层挂多少个 libc 函数：

| 档位 | 值 | 覆盖 | 什么时候用 |
|---|---|---|---|
| 最小 | 1 | `open/open64/__open_2/fopen/fopen64/access/stat`（7 个主路径） | 处理后 App 网络/图片异常时降到这档 |
| 标准 | 2 | + `faccessat/lstat/openat/openat64/__openat_2/readlink/readlinkat` | 防「按 fd 反查路径」那类取证 |
| 完整 | 3 | + `openat2/statx/opendir`（默认） | 与历史行为一致 |

**为什么要这个开关**：全量 hook 会把目标 App 的**正常**文件访问一起重定向到
`origin.apk`。上游实测 JMComic：只做 Java 层 → 无盗版警告且网络正常；
加上 native 层 → 网络与图片加载全部失败。因为 18 个 libc 函数里有一些被
App 自己的代码路径依赖，重定向后它读不到期望的资源。

档位数值是**跨语言协议**（对应 native 的 `NC_HOOK_LEVEL_*`），改一个数
就是协议变更。`UncheckPipeline.HookLevel` 与测试都把 [1,3] 与默认值钉住了。

### `extractNativeLibs` 必须是 true（上游藏了 4 天的坑）

目标包 `extractNativeLibs="false"` 时，系统安装**不解压** `.so`，
`nativeLibraryDir` 是空目录 → `System.load()` 必然失败 → native hook 从未加载。

真机证据（修复前）：
```
/data/app/<pkg>/lib/arm64/        → 空目录
/proc/<pid>/maps 搜 usign         → 无
logcat: SigFix: 找不到 native 库 ... 跳过 native 重定向
```

**全程无报错**：构建绿灯、装得上、Java 层去校验有效，只有 `logcat -s USign`
能看到那一行 warn。ApkForge 在 `UncheckPipeline` 第 ⑤ 步就改写这个属性
（`AxmlBoolean`，属性不存在时新增），并有自检兜底。

### 踩过的三个坑

| 坑 | 症状 | 修法 |
|---|---|---|
| dex 文件可写 | `SecurityException: Writable dex file is not allowed` | 写完 `setReadOnly()` |
| `attachBaseContext` 阶段 Context 未就绪 | `getCodeCacheDir()` NPE | 检测到未就绪就 return 且**不置完成标记**，靠多注入点重试 |
| 类加载器隔离 | handler 里读静态字段全是 null | 数据一律经构造器传入，不读 static |

## 6. 载荷为什么要「下载」而不是打进 App

载荷会被**注入到别人的 App 里执行**，且随目标行为 / Android 版本不断调整。
打进 ApkForge 意味着每改一次载荷就要发一次 App 版本。

```
json 仓库（gitee 镜像）
└── backend/uncheck/
    ├── index.json      版本 + 每个文件的 sha256
    ├─��� boot.dex        11416 B
    └── payload.dex     11884 B
```

### 安全前提：必须校验 sha256

下载的 dex 会被执行。不校验 = 信任整条网络链路。
`index.json` 里带每个文件的 sha256，**校验不过直接丢弃**，绝不「先用着再说」。

### 缓存策略

按 `index.json` 的 `version` 分目录：`filesDir/uncheck/<version>/`。
同版本不重复下载；版本变了才重拉。

## 7. AXML 改写的两个致命细节

**这两点写错时症状完全一样**：系统读不到 `android:name`、App 照旧实例化原类、
**没有任何报错**。这是本模块最难排查的一类问题。

### ① 属性必须插在 resourceId 升序位置，不能追加末尾

`PackageParser` 解析 `<application>` 时按 framework 资源 ID **升序**读，
遇到乱序**提前停止扫描**，后面的属性全部丢弃。

`android:name` 的 ID 是 `0x01010003`，在这批属性里最小 → 必须插最前。

对照 MT 生成的包（`JMComic3v2.1.14_kill.apk`）逐字节验证：

```
MT  : [3]  41000000 03000000 4d000000 0800 00 03 4d000000   ← 插在第 4 位
错误: [11] ...                                              ← 追加到末尾，系统读不到
```

### ② rawValue 必须是字符串池索引，不是 NO_INDEX

属性 20 字节布局：

```
ns(4) name(4) rawValue(4) size(2) res0(1) dataType(1) data(4)
```

`rawValue` 与 `typedValue.data` **都要填字符串池索引**（两者相同）。
写成 `NO_INDEX(0xFFFFFFFF)` 时 androguard 和系统都读不出值。

原包自带的 `appComponentFactory` 就是这个形态（`raw=0x2e data=0x2e`），可直接对照。

### 验证方法（三层，缺一不可）

```bash
# 1) 自己的解析器能读回（最弱，只能发现读写不一致）
#    在 App 内由 AxmlEditor.getAppName() 自检

# 2) androguard 也能读回（独立实现，能发现"自洽但都错"）
#    见 artifact-pipeline/scripts/uncheck/tests/test-axml.py

# 3) 装机后看系统是否识别（唯一权威判据）
adb shell "dumpsys package <pkg> | grep -oE 'ApplicationInfo\{[^}]*\}'"
#   能看到 className=<我们的类> 才算真的生效
```

> **教训**：只验「自己写的读函数能读出自己写的写函数的结果」是**自洽检查**，
> 两边错得一样时测不出来。必须有独立实现的交叉验证 + 最终的系统级判据。

## 8. 能力边界（对用户可见，界面上也写了）

| 校验读取途径 | 覆盖 | 说明 |
|---|---|---|
| `getPackageInfo().signatures` | ✅ | |
| `getPackageInfo(GET_SIGNING_CERTIFICATES).signingInfo` | ✅ | |
| `getApkContentsSigners()` / `getSigningCertificateHistory()` | ✅ | 两份数组都改 |
| `checkSignatures()` | ✅ | 同一个 `IPackageManager` |
| `getPackageArchiveInfo(自身路径)` | ✅ | 走同一接口 |
| App 自读 APK 文件算哈希 | ✅ | **native 层 IO 重定向**：`open(base.apk)` → `origin.apk`（2026-11 接入） |
| native so 解析 Signing Block（`open`/`fopen`/`__open_2`/`stat`…） | ✅ | 同上，shadowhook inline hook 覆盖 17 个路径类函数 |
| native **内联 `svc #0`** 直接系统调用 | ❌ | 指令长在调用方函数体里，无符号、无独立函数，inline hook 无从下手 |
| native **硬编码证书哈希**（`memcmp` 常量） | ❌ | 需逆向该 so 逐个 patch |
| 上报服务端裁决 / Play Integrity | ❌ **无解** | 本地无法胜出 |

后三类是**结构性无解**，不是「还没做」。工具不会假装能处理它们。

> ⚠️ **native 层生效有三个前提**，缺一个就只剩 Java 层（而 Java 层对
> 「自读 APK」类校验完全无效）：
> 1. 载荷含 `libusign_{arm64,armv7}.so`（索引里缺就报错，不产残缺载荷）
> 2. 目标包 `extractNativeLibs` 为 `true`（本模块会自动改写/新增该属性）
> 3. 目标包有 v2/v3 签名块（否则 `origin.apk` 里读不到证书，会在结果里报告）

## 9. 实现结构

```
core/axml/
├── AxmlManifest.kt        AXML 只读解析（包名 / LAUNCHER / Application）
├── AxmlEditor.kt          AXML 改写（android:name + 通用布尔属性）
└── AxmlBoolean.kt         extractNativeLibs 原位改写（属性不存在时新增）

core/apk/
├── ZipCentralDirectory.kt ZIP 中央目录解析（条目全元数据，数据复用要用）
├── ApkSigningBlock.kt     APK Signing Block 的提取与注入
└── ApkRepackager.kt       dex 注入用的重打包（与去校验不共用）

core/uncheck/              ★ 全部纯 JVM，可单测
├── CertExtractor.kt       签名块 → 证书 DER
├── UncheckPayload.kt      载荷模型 + index.json 解析 + sha256 校验 + 落点常量
├── ZipReuse.kt            数据复用（origin.apk 与整包共享字节）
└── UncheckPipeline.kt     九步主流程编排

data/uncheck/
└── PayloadFetcher.kt      下载 + 缓存（唯一需要 Context 的地方）

feature/uncheck/           状态管理（含 LogState，日志可一键复制）
ui/screen/uncheck/         Compose 界面
```

### 分层理由

`core/uncheck/` **刻意不碰 Android API**。这不是洁癖：这个模块的失败形态
全是「不报错」——

```
Manifest 改错    → 系统读不到 android:name → App 照旧跑原类
签名块没搬       → native 层读不到证书 → 静默只剩 Java 层
extractNativeLibs 没改 → .so 不解压 → System.load 失败但不崩
```

这些只能靠 JVM 单测提前拦住，靠点 UI 验证等于闭眼改二进制
（`AGENTS.md` §1.1）。

### 数据复用为什么要手写 ZIP

`java.util.zip` 表达不了「两个条目共享同一片物理字节」，而这正是让
`origin.apk` 不占第二份体积的唯一办法。所以 `ZipReuse` 自己算
local header / 中央目录 / EOCD 的每个字段。

**三条实测红线**（都固化成了测试）：

| 红线 | 违反后果 |
|---|---|
| origin 的 header 必须补到 4096 | 平移量不是 4 的倍数 → `resources.arsc` 失去对齐 → **装机被拒** |
| LFH 与中央目录的 extra 长度必须一致 | 读取方从 CD 拿 `extraLen=0` → 等于没对齐 |
| 产物之后绝不能再跑 apksigner / zipalign | 它们重写 ZIP，把重叠条目展开 → **体积翻倍** |

### 复用能力来自哪

| 已有组件 | 用途 |
|---|---|
| `core/apk/ZipCentralDirectory` | 复用要每个条目的完整元数据 |
| `core/apk/ApkSigningBlock` | 把原包签名块搬进中间包（origin.apk 才带证书） |
| `core/axml/AxmlManifest` | 读包名 / 原 Application |
| `data/FilePicker` | 选 APK（MT 优先 + 系统降级） |
| `ui/lifted/*` | 全部界面组件 |
| `LogState` | 日志面板 + 一键复制 |

**没有复用 `DexCallInjector`**：新方案不插 `invoke-static`，只改 Manifest。


### 复用了什么

| 已有组件 | 用途 |
|---|---|
| `core/apk/ApkRepackager` 的 zip 思路 | 组装时保持原条目压缩方式 |
| `core/axml/AxmlManifest` | 读包名 / LAUNCHER（只读，与 writer 分离） |
| `data/FilePicker` | 选 APK（MT 优先 + 系统降级） |
| `ui/lifted/*` | 全部界面组件 |
| `LogState` | 日志面板 + 一键复制 |

**没有复用 `DexCallInjector`**：新方案不插 `invoke-static`，只改 Manifest。

## 10. 调试：日志在哪

界面上有日志面板，**自带复制按钮**。失败时一键复制完整堆栈，
不需要装 adb、不需要会看 logcat。

日志包含每一步（读取 APK / 提取证书 / 改写 Manifest / 组装 / 自检）
与完整异常堆栈。

### 装机后的运行期日志（需要 adb）

```bash
adb logcat -s SigFixApp:* SigFix:* SigFixImpl:*
```

正常应该是这个顺序：

```
SigFixApp: hook 安装完成（早于原 Application 初始化）
SigFixApp: 配置已读取：cert 888 字符，originalApp=com.x.xiApplication
SigFixApp: mBase 已清零
SigFixApp: 已调用原 Application.attachBaseContext
SigFixApp: mInitialApplication 替换成功（回读一致）
SigFixApp: 已接管原 Application: com.x.xiApplication
SigFixApp: 已转发 onCreate 给 com.x.xiApplication
SigFixImpl: 伪造证书就绪，DER 666 字节
SigFixImpl: 隐藏 API 可访问 ✓
SigFixImpl: ✓ PackageInfo.CREATOR 替换成功（回读一致）
SigFixImpl: 签名伪造已生效，证书指纹=88294155c8fce454
```

**一条日志都没有** → `android:name` 没生效，回去查第 7 节的两个细节。

### 签名工具的硬约束（必须在界面上告知）

数据复用让 `origin.apk` 与整包**共享物理字节**。任何会重写 ZIP 的签名工具
都会把重叠条目**展开成两份**：

```
127.96 MB 复用包 --apksigner--> 255.6 MB     ← 复用完全失效
127.96 MB 复用包 --MT 管理器--> 128 MB       ← 手写 ZIP，保持复用
```

所以产物必须用 **MT 管理器之类手写 ZIP 的工具**签，不能用 `apksigner`。
ApkForge 不签名（与仓库固有契约一致），但这条已写进成功卡片的提示文案。

## 12. 与「hook 框架」的关系（另一个需求，别混）

本模块的核心仍是**改数据**：改 Manifest 让载荷挂到最早时机，再由载荷改
系统返回值（`PackageInfo.signatures`）。它不做「拦截任意方法调用」——
后者在 Android 17 上纯 Java 做不到（YAHFA/Pine 都停在 Android 12）。

### native 层用到了 ShadowHook，但只用于文件 IO

2026-11 接入的 `libusign.so` 用字节跳动 ShadowHook（inline hook）把
目标进程里所有指向 `base.apk` 的**路径类 libc 函数**重定向到 `origin.apk`：

```
open open64 __open_2 openat openat64 __openat_2 openat2
fopen fopen64 access faccessat stat lstat statx
readlink readlinkat opendir
```

它**只 hook 文件路径**，不 hook 任意 Java/native 方法。这两件事必须分清：

| | 本模块 | 「运行时 hook 框架」（是另一个产品） |
|---|---|---|
| 能力 | 改系统返回的数据 + 重定向 APK 文件路径 | 拦截任意方法调用、看参数、改返回值 |
| 依赖 | ShadowHook（仅 libc 路径类函数） | 需要更完整的 hook 框架 + 自写 JNI 桥 |
| 适用 | 签名校验这类「读数据」的校验 | 任意逻辑劫持 |

**为什么必须用 ShadowHook 而不是 PLT/GOT hook**：不同目标 so 的导入表各不
相同 —— 有的用 `__open_2`（`_FORTIFY_SOURCE` 把 `openat` 编成了它）、
有的用 `fopen`、有的根本没有 `openat`。实测踩过：「只挂
`open/open64/openat/openat64` 的 PLT hook 完全无效，因为目标 so 导入的是
`__open_2`/`fopen`」。

**注意 ShadowHook 的一处必需补丁**（Android 16 上）：`sh_linker_init()`
取不到 linker 私有符号时会让整个 init 失败（errno 12），必须降级为警告。
详见 artifact-pipeline 的 `docs/签名校验接手文档.md` §2.5。
