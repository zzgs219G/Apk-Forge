# 流程文档

注入流水线的完整数据流与每一步的实现细节。

---

## 总览

```
Input: sourceApk, targetClass?, targetMethod?, mode, callsText, payloadDex?, extraAssets
  │
  ├─[1] 读 AndroidManifest.xml ──▶ AxmlManifest.parseBytes ──▶ packageName, launchers
  │
  ├─[2] 定注入点 ──▶ targetMethod 为空 ? 自动 : 用户指定
  │      └─ ClassInspector.inspect ──▶ LifecyclePoints.resolve（native 自动降级）
  │           └─ InjectionPlanner.plan(mode, …) ──▶ 落点清单（1~6 个）
  │
  ├─[3] SmaliCallParser.parseAll(callsText) ──▶ List<Call> + errors（逐条进日志，不省略）
  │
  ├─[4] 遍历 classes*.dex ──▶ DexCallInjector.containsClass ──▶ hitDex
  │
  ├─[5] 逐落点 DexCallInjector.inject(hitDexBytes, spec) ──▶ newDexBytes
  │      （后一个落点接着前一个的产物继续改）
  │
  ├─[6] 校验 payloadDex 魔数 ──▶ payloadBytes?
  │
  └─[7] ApkRepackager.repack ──▶ 中间产物
       │       （替换目标 dex + 追加 payload + 写入 extraAssets，如同名则替换）
       └─[8] OutputStore.saveApk ──▶ Download/ApkForge/xxx_injected.apk
            │
            └─[9] TaskStore.add ──▶ 任务记录（包 + 配置 + 落点 + 产物）
```

### 进度与日志从哪来

有**两条通道**，分别对应「里程碑」和「高频状态」：

| 通道 | 谁在用 | 进日志列表？ | 用途 |
|---|---|---|---|
| `onStep(Step)` | 流水线各阶段 | ✅ 会一直留在历史里 | 里程碑：命中类、池注入、签名失效警告 |
| `onTick(progress, line)` | 大条目压缩 / 池注入各阶段 | ❌ 只覆盖那一行 | 「此刻在做什么」 |

**为什么必须分开**：`classes2.dex` 12.5MB 压缩要 2 秒，
按 256KB 分块会回调 50 次。若这 50 次都进 `steps`，
日志会被「写入 classes2.dex 42%」刷屏，真正的里程碑全被挤没。

`Step` 自带坐标，UI 不需要猜：

| 字段 | 用途 |
|---|---|
| `stage` | `Stage` 枚举，带 `weight`（重打包 4 / 注入 3 / 定位 2.5 / 其余 1） |
| `sub` | 阶段内完成度 0~1 |
| `progress` | `progressOf(stage, sub)` 折算的全局 0~1 |
| `atMs` | 相对开始的毫秒偏移，日志左侧 `+1.24s` |

阶段权重相加为分母，所以阶段交界处**连续不跳变**：
`progressOf(REPACK, 0f)` 紧接着上一段结束时的值。`LifecyclePointsTest` 钉住
「单调不减、落在 [0,1]、最后收在 1.0」。

#### 哪些地方会上报 onTick

1. **重打包的大条目**（`ApkRepackager.onBytes`）
   按 256KB 分块，每块回调 `(已写, 总长)` → UI 显示
   `写入 classes2.dex  42%  5.2MB/12.5MB`
2. **池注入的各个阶段**（`PoolInjector` 的 `lap()` → `onStage`）
   → UI 显示 `重写注解  ·  10b-annot-done 15334`

两处都做了节流：`ConsoleViewModel` 里限制「百分比变化 ≥2% 才 `state.copy`」，
否则每 256KB 就触发一次 Compose 重组，反而和压缩抢主线程。

日志快速刷屏的真实来源是重打包：`ApkRepackager.repack(onEntry = …)` 每写一个 entry 回调一次。
条目上千时按总量切成 ~60 段采样——全量上报会把日志刷成噪音，反而看不出「在动」。

#### 那 2 秒「卡住」是怎么来的（已修）

用户反馈：「从 0.8 秒突然卡到 2 秒」。日志长这样：

```
+0.81s  [定位目标类] 注入模式  单次注入 · 1 个落点
+2.12s  [注入调用] 注入调用（增量）  ... 1140ms ...
```

中间 1.31 秒空白——**那是注入本身**，之前只在结束时产生一条 step。
现在池注入的 `lap()` 会实时上报阶段名，这段空白被填上了。

## Step 1 — 解析 AndroidManifest

`ApkRepackager.readEntry(apk, "AndroidManifest.xml")` 取出原始字节，交给 `AxmlManifest.parseBytes`。

**全程只读字节，不产生文本 Manifest。**

AXML 结构：

```
RES_XML_TYPE (0x0003) 文件头
 ├─ RES_STRING_POOL (0x0001)    字符串池
 ├─ RES_XML_RESOURCE_MAP (0x0180)
 ├─ RES_XML_START_ELEMENT (0x0102)  ← 靠它拿元素/属性
 └─ RES_XML_END_ELEMENT (0x0103)
```

每个 chunk 头统一 `type(u16) headerSize(u16) size(u32)`。

### START_ELEMENT 的布局

```
偏移  字段
 8    lineNumber(4) comment(4)
16    ns(4) name(4)
24    attributeStart(u16) attributeSize(u16) attributeCount(u16)
      idIndex(u16) classIndex(u16) styleIndex(u16)
36    属性数组，每项 attributeSize（默认 20）字节：
        ns(4) name(4) rawValue(4) typedValue{ size(2) res0(1) dataType(1) data(4) }
```

属性取值优先级：`rawValue` 索引 > `dataType == TYPE_STRING` 的 data。

**为什么优先 rawValue**：对字符串型属性它总是给原始文本，比 data 索引更稳（某些 aapt2 版本会输出指向同一字符串池但索引不同的形态）。

### LAUNCHER 判定

维护一个元素深度栈，只关心：

- `manifest` → 取 `package`
- `activity` / `activity-alias` → 记下 `name`，开始收集
- `action` → `android.intent.action.MAIN`
- `category` → `android.intent.category.LAUNCHER`

`END_ELEMENT` 时若两者都命中，把类名归一化后加入结果。

**类名归一化**（`normalizeClassName`）：

| 输入 | package | 输出 |
|---|---|---|
| `.MainActivity` | `com.foo` | `com.foo.MainActivity` |
| `MainActivity` | `com.foo` | `com.foo.MainActivity` |
| `com.foo.MainActivity` | `com.foo` | `com.foo.MainActivity` |

## Step 2 — 定注入点

用户只做两件事：选 APK、选配置。**类名与方法名都是自动推出来的**，但要看得见、改得动。

### 2.1 类名

选完包立刻读 Manifest（Step 1），取 `primaryLauncher` 填进「注入点类名」。
多个 LAUNCHER 时给快捷 chip；用户也可以手打全类名，输入静默 320ms 后重新探测
（每敲一个字都开 zip 会卡）。

### 2.2 方法：先看类里真有什么

`ClassInspector.inspect()` 返回目标类的父类与全部方法（含 `isNative` 标记）。
父类决定用哪套清单：`Activity` 系走 `LifecyclePoints.ACTIVITY`，
`Application` 系走 `APPLICATION`。

每个候选点有三态：

| 状态 | 含义 | 后果 |
|---|---|---|
| `EXISTS` | 类里有同名同签名的方法 | 覆写加固，插在方法第一条指令前 |
| `MISSING` | 类里没有 | 新建方法：父类 super 调用 + 注入 + return |
| `NATIVE` | 有但是 native，没字节码 | **插不了**，必须换点 |

### 2.3 native onCreate 的自动降级

加固壳 / `NativeActivity` 的 `onCreate` 常是 native。这不是错误，是**需要重新决策的输入**。

`LifecyclePoints.resolve()` 按「时机接近度」降级：

```
onCreate(native)
   ↓
onPostCreate(Bundle)   ActivityThread.callActivityOnPostCreate，onCreate 返回后立刻调，
                       参数就是同一份 savedInstanceState —— 语义最接近
   ↓
onStart()              同一帧内紧随其后
   ↓
onResume()             可交互时机
   ↓
attachBaseContext(Context)  更早，但还没有 Activity 窗口，要 Activity 参数的载荷放最后
```

三条约束：

1. 只有 `NATIVE` 才降级，`MISSING` 不降级（没有就新建，框架照样会调）；
2. 替代点必须来自**同一个类的可用清单**——对 `Application` 不能推荐 `onPostCreate`；
3. 原因必须回传到 UI（`Resolution.reason`），这是系统替用户做的决定，不能说悄悄话。

`LifecyclePointsTest` 的 5 个降级用例钉住以上三条，其中包括「整类生命周期都是 native」
这个极端场景：此时如实报「没有其它可插的点」，而不是随便挑一个。

### 2.4 模式决定铺几个点

`InjectionPlanner.plan(mode, points, methods, wanted)` 把「模式」翻译成落点清单：

| 模式 | 落点 | 说明 |
|---|---|---|
| `ONCE` | 1 个 | 沿用 `resolve()` 的结论（含 native 降级），不扩点 |
| `EVERY_ENTER` | ≤2 个 | `onStart` + `onResume`，已含的自动去重 |
| `MULTI_POINT` | ≤6 个 | 所有非 native 点 |
| `REPLACE_BODY` | 1 个 | 同一个点，但 `DexCallInjector.Spec.replaceBody = true` |

三条硬约束（`InjectionModeTest` 7 例钉住）：

1. 落点只能来自**同一个类**的清单（`points` 由父类决定），`Application` 不能拿到 `onPostCreate`；
2. `NATIVE` 一律排除——它没有字节码，插进去只会产出非法 dex；
3. `ONCE` 不许为了「模式需要」重算一遍 `resolve()`，否则 native 降级会失效。

**为什么判定必须收在一处**：这三个约束只要有一处实现漂了，症状都是
「注入成功但行为为零」——日志全绿、产物正常、效果没有。那是没有报错的失败。

### 2.5 签名从哪来

一律来自 `LifecyclePoints` 里的常量（`(Landroid/os/Bundle;)V`、`()V` 等），
用户看不到也改不了。理由：签名写错会新建出一个**永远不会被系统调用**的方法，
表现为「注入成功但没效果」——最难查的那类失败。
`LifecyclePointsTest.注入点清单里每个签名都能被解析器认下` 钉住这些常量的正确性。

### 2.6 注入点确定了，往下走

确定后的 `(name, signature)` 传给 Step 5，后续流程与旧版一致。

## Step 3 — 解析 smali 调用

### 支持的形态

```smali
invoke-static {p0}, Lcom/foo/Bar;->init(Landroid/app/Activity;)V
invoke-virtual {p0, v1}, Lcom/foo/Bar;->doIt(I)V
invoke-direct {p0}, Lcom/foo/Bar;-><init>()V
invoke-super {p0, p1}, Lcom/foo/Base;->onCreate(Landroid/os/Bundle;)V
invoke-interface {p1}, Ljava/lang/Runnable;->run()V
invoke-static/range {p0 .. p2}, Lcom/foo/Bar;->x(III)V
invoke-static {}, Lcom/foo/Bar;->noArg()V
```

`#` 注释与空行忽略。**一行出错不影响其它行**——用户粘一大段时，只应为那一行报错。

### 正则

```kotlin
HEADER     = ^(invoke-[a-z\-]+(?:/range)?)\s*\{([^}]*)\}\s*,\s*(.+)$
METHOD_REF = ^(L[^;]+;)\s*->\s*([^\s(]+)\s*\(([^)]*)\)\s*(\S+)$
```

### 寄存器列表

- 非 range：`{p0, v1}` → `["p0", "v1"]`，每项必须匹配 `^[pv]\d+$`
- range：`{p0 .. p2}` → 展开成 `["p0","p1","p2"]`，要求同族（都是 p 或都是 v）且 `to >= from`

### 参数类型解析

手写扫描器，支持 `L...;`、`[...`（数组）、`ZBSCIJFD`（基本类型）：

```
Landroid/app/Activity;ILjava/lang/String;  →  [Activity;, I, java/lang/String;]
[B                                          →  [[B 的数组形态]
```

## Step 4 — 定位 dex

**先做一次结构检查**（`PackIntegrity.inspect`），再逐 dex 找类。

结构检查只读 dex 头部，认四种确定性证据：魔数不是 `dex\n`、
`file_size` 与实际字节数不符、`header_size` ≠ `0x70`、
声明了类却没有任何字符串。判断方式刻意不数阈值（类数多少、assets 里有没有 jar），
理由见 `踩坑记录.md` 坑 33——那两个判据实测都会误报正常包。

只有**所有** dex 都不可读时才拦截（`blocked`）：只要还有一个能读，注入就有机会成功，
此时应提示而让下游按「找不到类」如实报错，不提前拒绝。

```kotlin
for (name in ApkRepackager.listDexNames(apk)) {
    val bytes = readEntry(apk, name) ?: continue
    if (DexCallInjector.containsClass(bytes, ownerType)) { hitDex = name; break }
}
```

**必须逐 dex 找，不能全加载**：21 dex 的大包在手机上内存扛不住。`DexBackedDexFile` 是 lazy 的，只读类定义表不解析方法体，所以扫 30MB 包也是秒级。

`containsClass` / 解析都必须用 `DexOpcodes.forBytes(bytes)` 取 opcodes，
**不能用 `Opcodes.getDefault()`**：后者是 api=20 ↔ dex 035，会让 039 的宿主 dex
在重写时丢掉版本号（`踩坑记录.md` 坑 30）。

dex 名排序：

```kotlin
sortedBy { name ->
    val n = name.removePrefix("classes").removeSuffix(".dex")
    if (n.isEmpty()) 1 else n.toIntOrNull() ?: Int.MAX_VALUE
}
```

`classes.dex` 排第一（`n` 为空视为 1），然后 `classes2.dex`、`classes3.dex`…

## Step 4.5 — 幂等检查（每个落点注入前）

```kotlin
when (val verdict = InjectIdempotency.check(input.sourceApk, spec)) {
    is AlreadyInjected -> { 记录「跳过重复注入」警告; return@forEachIndexed }
    Clean, Unknown -> Unit
}
```

判据是**精确重复**：owner + 方法名 + 参数 + 返回值全一致，且落在方法**开头**连续位置。
不看「载荷类是否被调用过」——同一个载荷类完全可能有第二个方法要插。

只比开头那几条的原因：注入点在最前面，深处的相同指令是宿主自己的代码。
换一条不同的调用行（换方法名 / 换参数类型）算合法新增，不拦。

全部落点都被跳过时**报失败**并说明原因，不产出「和源包一样」的包——
那种产物会让用户以为注入成功了。

## Step 5 — 注入

### 5.1 定位目标方法

```kotlin
// ⚠️ 关键：dexlib2 的 methods 每次访问都新建对象
val classMethods = targetClass.methods.toList()
val existing = classMethods.firstOrNull {
    it.name == spec.methodName && signatureOf(it) == spec.methodSignature
}
```

`DexBackedClassDef.methods` 每次访问返回新对象，所以**必须先物化成 List**，后续定位与替换都基于同一批对象。用 `it === targetMethod` 做身份比较永远为 `false`，改写会静默失效。

### 5.2 寄存器换算

```kotlin
// p 区起点 = 总寄存器数 - 参数寄存器数
// 实例方法参数寄存器数 = 参数个数 + 1（含 this）
val paramRegCount = paramTypes.size + 1
val p0 = registerCount - paramRegCount
```

`p_i` → `registerCount - paramRegCount + i`
`v_i` → `i`（且必须 `< registerCount`）

### 5.3 指令形态选择

```kotlin
// 35c 最多 5 个寄存器，且编号 <= v15
val fits35c = phys.size <= 5 && phys.all { it <= 15 }
val contiguous = phys.isEmpty() || (phys.max() - phys.min() + 1 == phys.size)
```

| 情况 | 处理 |
|---|---|
| `fits35c` | `35c`（`invoke-*`） |
| 超 5 个 / 有 >v15，且连续 | `3rc`（`invoke-*/range`），自动降级 + 记 warning |
| 需要 range 但不连续 | **直接报错**，不产出非法 dex |

### 5.4 新建方法

方法不存在时：

```
registerCount = paramTypes.size + 1   // 恰好覆盖 p 区，不额外申请
accessFlags   = ACC_PUBLIC
方法体：
  [0] invoke-super/range {p0 .. pN}, <super>;-><sameName>(<sameSig>)   ← 若父类有
  [1..] 注入的调用
  [last] return-void（或 RETURN / RETURN_WIDE / RETURN_OBJECT，按返回类型兜底）
```

**父类调用判定**：

```kotlin
val superType = cls.superclass ?: return null
if (superType == "Landroid/app/Object;") return null
// 其余情况只要有同名同签名就补
```

不用方法名白名单的理由：白名单（只认 `onCreate`/`onResume`/…）会漏掉 `onNewIntent`、`onPostCreate` 这些同样需要 super 的生命周期方法，也会让用户在自定义方法上观察不到行为差异。

`Application.onCreate` 是空实现，理论上可以不调，但保持一致性更安全（父类可能是自定义 Application 并覆写了 onCreate）。

### 5.5 写出

**有两条路径，先试快的，不适用再退全量。**

#### 快路径：`PoolInjector`（增量，实测注入 1.1 秒）

```
FastInjector.tryInject()
    └─ 粗筛（不通过就返回 NotApplicable，由上层回退）
        ├─ 替换方法体模式 → 回退（要丢弃原指令）
        ├─ 方法不存在需新建 → 回退（要改 class_data 结构）
        └─ 目标方法带 try/catch → 回退（要重算 try 项偏移）
    └─ PoolInjector.addMethodRef()  ← 核心
        ├─ 1~9.  池重排：新增字符串/类型/proto/方法，算出「旧下标 → 新下标」映射
        ├─ 10.   逐段产出：string_data / type_list / annotation / debug_info /
        │        code_item / class_data / 6 张 id 表，每个段各自一个缓冲
        ├─ 11.   class_data 必须最后生成（它的 code_off 是 uleb128 变长，
        │        要写成**最终绝对偏移**，所以得先知道 code_item 段基址）
        ├─ 12.   DexSectionLayout 按 ART 规范段序拼接，段间零填充、同 type 连续
        ├─ 12a.  回填交叉引用：string_ids → string_data、class_def → 各段、
        │        proto → type_list、code_item → debug_info、注解四结构互指
        └─ 12b.  回填指令里的池索引（只处理真正变了的，约 8.5%）
```

**关键设计：`Invoke` 指令的 method_idx 位置留空**，由 `PoolInjector` 算好
`newMethodIdx` 后填入（`InsnPatch.methodIdxWord`）。

这样「登记方法」和「插入调用」在**同一次池重排**里完成。若拆成两次调用，
每遍都产出一份完整 dex，30MB 级别会直接 OOM
（实测 `Failed to allocate a 29989720 byte allocation`）。

#### 慢路径：`DexCallInjector`（全量，9~18 秒）

```kotlin
val store = MemoryDataStore()
DexPool.writeTo(store, newDexFile)
```

`DexPool` 会重建整个 dex 的字符串/类型/方法池。**dex 版本头保持原样**，
不做任何回填——这是与 apktool 路线最重要的差异。

它是**正确性保底**：任何快路径不支持的形态都能走这里。

#### 两条路径的选择

`FastInjector.Result` 有三种：

| 结果 | 含义 | 上层动作 |
|---|---|---|
| `Injected` | 增量成功 | 直接用 |
| `NotApplicable(reason)` | 增量不适用 | 回退全量，**并把 reason 显示给用户** |
| `Failed(reason)` | 增量出错 | 回退全量 |

`NotApplicable` 不是错误，但**必须把原因说清楚**——否则用户看到耗时差异
会以为是随机波动，而不是「这个包不支持快路径」。

## Step 6 — payload dex 校验

只做一件事：验魔数。

```kotlin
require(raw.size > 8 &&
    raw[0]=='d' && raw[1]=='e' && raw[2]=='x' && raw[3]=='\n'
) { "payload 不是合法 dex（缺少 dex\\n 魔数）" }
```

防止用户误选 zip / jar / 普通文件。不做更深校验（比如解析全量 dex）——那是注入方（用户）的责任，我们只保证「不是明显错的」。

## Step 7 — 重打包

`ApkRepackager.repack`，核心约束：

### 7.1 原样拷贝所有条目，只替换目标 dex

```kotlin
val e = ZipEntry(src.name).apply {
    time = src.time
    // ⚠️ 压缩方式跟随原条目：STORED 的别改成 DEFLATED
    method = if (src.method == ZipEntry.STORED) ZipEntry.STORED else ZipEntry.DEFLATED
    if (method == ZipEntry.STORED) {
        size = data.size.toLong()
        compressedSize = data.size.toLong()
        crc = CRC32().apply { update(data) }.value
    }
}
```

`resources.arsc` 与 `AndroidManifest.xml` 必须是 STORED 且 4 字节对齐，重压缩会破坏它们。

### 7.1b 对齐必须靠 extra field 补回来

`ZipEntry` **不复制** extra field，而 AGP 把对齐填充正好放在 extra 里。
丢掉它之后所有 STORED 条目数据前移，实测 78 个条目失去 4 字节对齐、
`resources.arsc` 掉到 `off%4=2`、`.so` 失去 16KB 页对齐。

修法是**从源包反推每个条目原有的对齐**，不枚举文件名：

```
读源包的中央目录 → 每个条目的真实数据偏移
偏移 % 16384 == 0 → 原本按 16KB 对齐（16KB 页设备上的 .so）
偏移 % 4096  == 0 → 原本按 4KB 对齐
偏移 % 4     == 0 → 原本按 4 字节对齐（.arsc / .dex）
都不沾            → 本来就没对齐，不要凭空发明
```

写出时按 `当前流位置 + 30 + 名字长度` 算基准，用**裸 0 字节**补足差额
（与 AGP 一致，`zipalign -c` 也认）。

两个必须记住的推导细节：

1. **解析走中央目录，不能顺 local header 链爬。** `ZipOutputStream` 写 DEFLATED
   条目用 data descriptor（local header 的 `csize` 写 0），顺链走会停在第一个条目，
   于是「未对齐数 = 0」**假绿**。
2. **自检基准必须是源包的对齐要求。** 拿产物自己的偏移反推「它要求几字节」必然自证成功。

写完复核：`Stats.misalignedEntries` 非 0 时流水线报 warning，不等用户拿 zipalign 才发现。

### 7.2 Manifest 绝不解码

`AndroidManifest.xml` 与其他条目一样按字节原样搬运。任何「解码成文本再写回」的路径都会产出系统不认的灰包（见 `踩坑记录.md` 坑 1）。

### 7.3 payload 追加为下一个空闲的 classesN

```kotlin
var n = 2
while (existingNames.contains("classes$n.dex")) n++
addedName = "classes$n.dex"
```

时间戳固定为 0，与 AGP 产物一致，保证可复现。

### 7.4 不写额外资产：配置必须烘焙进 dex

`repack()` **没有** `extraEntries` 这类参数，这是刻意的：

```kotlin
repack(sourceApk, outputApk, targetDexName, newDexBytes, payloadDexBytes, onEntry)
```

注入一个包只应该让它多一个 `classesN.dex`。任何「顺手写个配置文件进去」的入口
都会变成第二条通道：资产没写成功 = 载荷读不到配置 = 注入成功但不弹窗，
而且**不报错**。入口不存在，这个错就犯不出来（详见 `踩坑记录.md` 坑 28）。

`InjectEndToEndTest` 钉住产物边界：条目数恰好 +1、原有条目一个不少、
多出来的只能是 `classesN.dex`、绝不能出现 `.json` / `.jsonc`。

### 7.5 产物是**未签名**的，不是「签名不匹配」

重写 zip 会让 APK Signing Block 必然丢失——`java.util.zip` 不会写回它，
写回也没用（dex 变了，签名不再匹配）。实测：

```
apksigner verify out.apk
  DOES NOT VERIFY
  ERROR: Missing META-INF/MANIFEST.MF
```

所以产物**任何设备都装不上**，必须自己用 MT / apksigner 重签。
`Stats.sourceHadSignature` 用来检测源包带不带 v2/v3 签名，流水线据此在日志里
如实报一条「签名已失效」——这比让用户装完了才莫名其妙失败要好。

## Step 7.5 — 插件包（弹窗载荷 + 配置烘焙）

```
payload/dialog/src/…/{PayloadDialog,PayloadConfig,PayloadUi,PayloadEvent,PayloadStore}.java
        │  sh payload/dialog/build.sh
        │    · javac（-source/-target 8，bootclasspath = android.jar）
        │    · API 兼容自检：再用 android-21/android.jar 编一遍
        │    · d8 → classes.dex
        │    · 占位符唯一性自检（必须恰好 1 次）
        ▼
payload/dialog/out/{PayloadDialog.dex, call.txt, apkforge-plugin.zip}
        │
        ▼  App 内「插件包」页：调弹窗每一项 → 导出
core/dex/PayloadBaker.bake(templateDex, json)
        │   把 PayloadConfig.baked() 的方法体换成 const-string + return-object
        ▼
烘焙后的自包含 dex ──┬─▶ 落 files/plugin/PayloadDialog.dex
                     └─▶ 打进 Download/ApkForge/apkforge-plugin.zip（dex + call.txt）
        │
        ▼  注入时 payloadDex 作为 classesN.dex 追加
宿主 classesN.dex（代码 + 配置，全在里面）
        │
        ▼  宿主启动
PayloadDialog.inject(Activity) → PayloadConfig.parse(baked()) → AlertDialog
```

**为什么配置在 dex 里而不是资产里**

| 维度 | 写进 assets（旧） | 烘焙进 dex（现在） |
|---|---|---|
| 产物新增条目 | `classesN.dex` + `assets/apkforge_dialog.json` | 只有 `classesN.dex` |
| 失败面 | 「资产写了」+「按路径读到了」两次握手 | 一次：dex 里有配置 |
| 改文案 | MT 改资产即可，不重注入 | 重新导出 + 重新注入 |
| 越界风险 | 改写了宿主自有资产 | 无 |

选后者：本地弹窗是「一次性投放」，改文案的频率远低于「产物干净 + 通道唯一」的价值。

**烘焙的三条硬约束**

1. 占位符 `__APKFORGE_CONFIG__` 必须由**方法返回**（`PayloadConfig.baked()`），
   不能写成 `static final String` —— 后者会被 javac 内联成多份拷贝，
   烘焙时无法确定替换哪一份。构建期数字节 + 单测双重钉住「恰好一次」。
2. 烘焙后必须**字节级**自检：占位符已消失、配置真的在里面。
   不能 `String(dex, ISO_8859_1).contains(...)` —— dex 字符串池是 MUTF-8，
   中文按 Latin-1 解出来永远匹配不上，会把成功误判成失败。
3. 反向也要能读：`PayloadBaker.extract()` 从烘焙好的 dex 里读回配置，
   导入插件包时用它恢复表单（zip 里只有 dex，没有配置文件）。

**载荷能力（对齐清羽弹窗 7.0）**

```
四道闸门：Activity 存活 → 总开关=开 → 不在静默期 → 智能 24h 间隔
三按钮  ：同意(左) / 拒绝(右) / 中立(中)，各自开关 + 文本 + 颜色 + 事件
五风格  ：默认暗 / 默认亮 / HOLO暗 / HOLO亮 / 传统
动作    ：无 / 网址 / 退出 / 提示 / 智能 / QQ名片 / QQ群 / QQ咨询
安全    ：scheme 白名单（http/https/mqqapi/mqqwpa），未知动作降级为「无」
兼容    ：老式拼串事件（`网址http://…提示跳转`）仍按原语义解析
```

**为什么载荷不联网**：它会被塞进别人的 App。一个会联网轮询的载荷，等于把
别人的设备变成你的客户端。配置烘焙在 dex 里，行为完全可解释、可离线验证。

**契约由 `PluginPayloadTest` 钉住**：调用行里的类名/方法名/签名必须与 dex 里
真实存在的方法逐字一致且为 `public static`；占位符全 dex 唯一；
烘焙往返逐字一致；7.0 老配置字段能归一化；未知动作降级成「无」。

## Step 8 — 写入 Download

`OutputStore.saveApk`。

### Android 10+：MediaStore

```kotlin
val values = ContentValues().apply {
    put(MediaStore.Downloads.DISPLAY_NAME, name)
    put(MediaStore.Downloads.MIME_TYPE, "application/vnd.android.package-archive")
    put(MediaStore.Downloads.RELATIVE_PATH, "Download/ApkForge")
    put(MediaStore.Downloads.IS_PENDING, 1)
}
val uri = contentResolver.insert(MediaStore.Downloads.EXTERNAL_CONTENT_URI, values)
// 写入后
values.clear(); values.put(IS_PENDING, 0)
contentResolver.update(uri, values, null, null)
```

免权限。`IS_PENDING = 1 → 0` 是必须的两阶段提交，否则其他 App 可能在写入中途看到半个文件。

同时按 `RELATIVE_PATH + DISPLAY_NAME` 反推出 `File` 路径，因为**安装 APK 和「MT 定位」都需要真实路径**，MediaStore 只给 content URI。两个形态都保留在 `Saved(file, uri)`。

### Android 9 及以下

直接 `File` 写入，失败则退回 `getExternalFilesDir`，保证有产出。Manifest 里 `WRITE_EXTERNAL_STORAGE` 带 `maxSdkVersion="28"`。

### 同名处理

```kotlin
var candidate = name
var i = 1
while (File(dir, candidate).exists()) { candidate = "$base-$i.$ext"; i++ }
```

不覆盖用户已有产物。

## 配置的存取流程

### 保存

```
用户编辑（ConfigViewModel）
  │
  ├─ dex 源文件可能来自 cacheDir（MT 选的）→ 系统随时会清
  │
  ▼
ConfigStore.upsert(id, name, calls, mode, assets, dexSource)
  │
  ├─ dexSource != null → 复制到 files/configs/<id>.dex
  ├─ dexSource == null 且已有 dex → **保留原 dex**（用户可能只改名字）
  ├─ assets 为空 → 保留原有 assets（同一条「只改名字别丢东西」的原则）
  └─ 写 files/configs/configs.json
```

**配置只描述「注入什么」**：调用行、payload dex、注入模式、附带资产。
**注入点（哪个类的哪个方法）不在配置里**——那是包自己的属性。
上一版把 `targetMethod` 塞进配置，换到别的包时会戳到那个包里不存在的方法，
表现为「注入成功、效果为零」（见 `踩坑记录` 坑 23 的同类问题）。

**「保留原 dex」是必须的**：不加这个判断，用户改个配置名会把 dex 弄丢。

### 读取

```kotlin
list() → 解析 configs.json，按 updatedAt 降序
```

`Config.dexPath` 指向的文件可能已丢失（用户清数据、手动删）。UI 层用 `hasDex` 判断并提示「dex 文件已丢失，请重新选择」，不假设它一定在。

## 测试策略

核心逻辑不依赖 Android API，所以直接在 JVM 上跑真实 APK：

```bash
sh gradlew :app:testDebugUnitTest
# 可指定 APK：
sh gradlew :app:testDebugUnitTest -Dapkforge.testApk=/path/to/target.apk
```

`app/src/test/` 的断言清单见 `项目介绍.md`。

**为什么必须这样测**：二进制改写靠点 UI 验证是不负责任的——出错了只会看到「闪退」，不知道错在哪。
`app/src/test/` 里已经有多条真 bug 是靠它抓出来的（见 `踩坑记录.md` 坑 2、坑 5、坑 23、坑 30~32）——
其中「dex 版本头被降级」「进度条倒退」两条都不是靠读代码发现的，是对着产物和 Step 序列断言才暴露的。

其中两类断言值得单独说明：

- **端到端**（`InjectEndToEndTest`）跑真实 APK：Manifest 逐字节不变、产物 dex 可解析、
  指令落在头部、替换方法体后只剩两条指令、额外资产进包且同名替换、重打包回调不重不漏；
- **契约**（`PluginPayloadTest`）不需要真机：调用行与载荷 dex 里的方法逐字对齐、
  必须是 `public static`、资产路径常量与载荷常量一致。这类错位全都会变成
  「注入成功但不弹窗」，只能靠断言提前拦住。
