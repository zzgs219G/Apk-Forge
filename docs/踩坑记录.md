## 坑 1 — 文本 Manifest 装回包会产出「灰包」

**现象**（来自参考工程 artifact-pipeline 的实证，本工程据此规避）

用 apktool `--force-manifest` 解出文本 `AndroidManifest.xml`，改完再 `apktool b -r` 装回包，产出的 APK 在 MT 里打开是灰的、系统不认、装不上。

**根因**

`-r`（不反编译资源）模式下，apktool 把文本 Manifest **原样拷贝**回 APK，不重新编成二进制 AXML。系统读到的是明文 XML，直接拒绝。

**修法（本工程的做法）**

从设计上不产生文本 Manifest：

- `AxmlManifest` 只**读**二进制，不写
- `ApkRepackager` 把 `AndroidManifest.xml` 和普通条目一样按字节原样搬运
- 需要改 Manifest 时应该做**二进制原位补丁**，不是解码重编

**教训**

> 「解码 → 修改 → 重编码」这种往返，每一对编解码器都是保真度风险点。
> 能不往返就不往返。二进制格式优先考虑原位补丁。

## 坑 2 — 注入静默失效：`dexlib2` 的 `methods` 每次访问都是新对象

**现象**

端到端测试报：

```
AssertionError: onCreate 首条指令应为 invoke-static，实际 IGET_OBJECT
```

注入函数返回成功、dex 也写出来了、产物 dex 结构合法——**唯独指令没进去**。

**根因**

```kotlin
// 错误写法
val targetMethod = targetClass.methods.firstOrNull { ... }
...
targetClass.methods.map { if (it === targetMethod) newMethod else it }
//                        ^^^^^^^^^^^^^^^^^^^ 永远 false
```

`DexBackedClassDef.methods` 每次访问都**新建** `DexBackedMethod` 对象（它是 lazy 视图，不是缓存列表）。所以 `it === targetMethod` 恒为 `false`，改写后的方法根本没被替换进类里。

**修法**

```kotlin
// 先物化，后续定位与替换都基于同一批对象
val classMethods = targetClass.methods.toList()
val targetMethod = classMethods.firstOrNull { ... }
...
classMethods.map { m ->
    if (m.name == targetMethod.name && sigOf(m) == sigOf(targetMethod)) newMethod else m
}
```

替换时用「方法名 + 签名」匹配，不用对象身份。

**教训**

> **`===` 身份比较在 lazy 集合上是陷阱。** dexlib2 的 `classes` / `methods` / `fields` 都是 `Set<out T>` 形式的 lazy 视图，
> 每次访问重新构造。凡是要「从中挑一个、改完放回去」的操作，必须先 `.toList()` 物化。
>
> 更一般的：**静默失效比崩溃危险得多**。这个 bug 所有返回值都正常、所有结构校验都通过，
> 只有「首条指令是什么」这个语义断言能抓到它。

## 坑 3 — `p0` 不是 `v0`：p/v 寄存器换算

**现象**（来自 artifact-pipeline 报错二十一，本工程预先规避）

往方法里插 `invoke-static` 时照抄了 `const-string` 的寄存器，smali 汇编阶段直接拒绝：

```
Invalid register: v19. Must be between v0 and v15
The maximum allowed register in this list is v15
```

**根因**

两条指令的寄存器编码宽度不同：

| 指令格式 | 寄存器位数 | 上限 |
|---|---|---|
| `const-string`（21c） | 8 bit | v0–v255 |
| `invoke-*`（35c） | **4 bit** | **v0–v15** |

Compose / Kotlin 的大方法里寄存器数轻松超 16，`p0` 换算成物理号可能落在 v19。

**修法**

```kotlin
val fits35c = phys.size <= 5 && phys.all { it <= 15 }
if (fits35c) {
    ImmutableInstruction35c(opcode, ...)
} else {
    // 3rc（/range）是 16 bit
    ImmutableInstruction3rc(opcodeRange, phys.min(), phys.size, ref)
}
```

外加不连续性检查：`3rc` 的寄存器区间是 `[start, start+count)`，`{v0, v5}` 这种不连续的直接报错。

**教训**

> **把一个操作数从「一种指令」搬到「另一种指令」时，必须同时校验目标格式的编码宽度。**
> 「不新增寄存器」只解决了数量问题，没解决宽度问题。

## 坑 4 — 新建方法不补 `super` 会让 Activity 崩溃

**现象**

注入到不存在的 `onCreate` 后，App 启动即崩，报错指向 Activity 内部状态。

**根因**

新建的方法体只有「注入的调用 + return-void」，没有 `invoke-super {p0, p1}, <父类>;->onCreate(Landroid/os/Bundle;)V`。

`Activity.onCreate` 内部要完成窗口挂载、`Instrumentation` 回调、生命周期状态推进。跳过它，后续任何生命周期回调都会撞到未初始化状态。

**修法**

```kotlin
// 新建方法体的第 0 条指令
if (created) {
    buildSuperCall(targetClass, methodName, signature, registerCount)?.let { body += it }
}
```

`buildSuperCall` 用 `invoke-super/range {pStart .. pStart+paramRegCount-1}`，正好覆盖整个参数区（range 要求连续，p 区天然连续）。

**教训**

> **「方法不存在就创建一个」不是填个空壳就完事**——要看清它原本承担什么责任。
> 生命周期方法是**覆写**语义，覆写的默认契约就是「调 super」。凭空造一个不做父类调用的实现，等于破坏了这个契约。

## 坑 5 — 父类调用判定用白名单会漏方法

**现象**

加了 `super` 调用后，测试仍失败：

```
新建方法应先调父类 onCreate，实际指令: [INVOKE_STATIC, RETURN_VOID]
```

**根因**

初版 `buildSuperCall` 硬编码了白名单：

```kotlin
if (methodName != "onCreate" && methodName != "onResume" &&
    methodName != "onStart" && methodName != "onPause") return null
```

测试用的探测方法名 `onCreateForgeProbe` 不在白名单里，于是被跳过。

**修法**

去掉白名单，改为「父类声明了同名同签名方法就补」：

```kotlin
val superType = cls.superclass ?: return null
if (superType == "Landroid/app/Object;") return null
// 其余情况一律补
```

**教训**

> **白名单是负债。** 硬编码枚举永远比实际世界少一项，
> 而且漏掉时**不报错、只是行为不对**。
>
> 更好的判据是「从数据里推」：父类有没有这个方法？有就补，没有就算了。
> 数据驱动 > 枚举。

## 坑 6 — KDoc 里的 `*/` 会提前闭合注释

**现象**

```kotlin
/**
 * 1. **寄存器宽度**：`invoke-*` 的 35c 格式仅 4 bit。
 *    超出必须换 `invoke-*/range`（3rc，16 bit）。
 */
```

编译报几十条：

```
Syntax error: Expecting a top level declaration.
```

**根因**

`invoke-*/range` 里的 `*/` 被解析器当成注释结束符。注释在那一行提前闭合，后面的 KDoc 文本被当成代码。

**修法**

拆开写：`` `invoke-` + `/range` ``。

**教训**

> 在注释里描述「通配符 + 斜杠」的组合时，`*/` 是必然踩的雷。
> 任何以 `*` 结尾的词紧跟 `/` 都要警觉：`*/`、`/*`、`//`。

## 坑 7 — `--offline` 按仓库标识匹配缓存

**现象**

```
Could not download profileinstaller-1.4.0.aar: No cached version available for offline mode
```

但这个 aar 明明在 `~/.gradle/caches/modules-2/files-2.1/` 里。

**根因**

Gradle 的模块缓存是**按仓库 URL 分键**的。改了 `settings.gradle.kts` 的仓库列表（加阿里云镜像、加 jitpack），之前从 `google()` 下载的条目在当前仓库配置下匹配不上，`--offline` 就认为没有缓存。

**修法**

联网跑一次先把缓存补齐，之后的 `--offline` 才有效。或者让仓库列表与当初下载时保持一致。

**教训**

> `--offline` 不是「只看本地文件」，是「只接受当前仓库配置下的本地文件」。
> 换仓库配置后第一次必须联网。

## 坑 8 — JDK 21 禁用了 `-bootclasspath`

**现象**

编译示例 payload dex 时：

```
error: option --boot-class-path not allowed with target 11
```

**根因**

JDK 9 引入模块系统后，`-bootclasspath` 被 `--release` / `--system` 取代。JDK 21 直接禁止它与其他 `--release` 混用。

**修法**

```bash
# 错误
javac -source 11 -target 11 -bootclasspath android.jar
# 正确：android.jar 当普通 classpath
javac --release 11 -classpath android.jar
```

**教训**

> 用 `android.jar` 当 bootclasspath 是老教程的写法，JDK 9+ 已不适用。
> `-classpath` 在绝大多数场景下等价且兼容。

## 坑 9 — `d8` 不能直接 `java -cp d8.jar` 调

**现象**

```
Error: Could not find or load main class com.android.tools.r8.D8
```

**根因**

`d8.jar` 不是可直接执行的 jar（缺 `Main-Class`，或主类名与直觉不同）。AGP 自带的 `d8` 是包装脚本，内部会拼好 JVM 参数。

**修法**

直接调脚本：`$ANDROID_SDK/build-tools/37.0.0/d8`。

**教训**

> 工具链里的可执行文件优先用它自带的包装脚本，别自己猜 `java -cp`。

## 坑 10 — `getExternalFilesDir` 的文件用户找不到

**现象**

注入成功了，但用户去文件管理器里找不到产物，以为失败了。

**根因**

初版写到 `/sdcard/Android/data/com.xixin.apkforge/files/output/`。

Android 11+ 的**分区存储**下，`Android/data/` 在系统文件管理器和多数第三方文件管理器里**默认不可见**，MT 也要单独授权才能进。

**修法**

改用 MediaStore 写入 `Download/ApkForge/`：

```kotlin
put(MediaStore.Downloads.RELATIVE_PATH, "Download/ApkForge")
```

Android 10+ 免权限，落盘位置就是用户熟悉的 Download。

**教训**

> **「能写进去」和「用户能找到」是两件事。**
> 输出路径的设计要按用户的浏览习惯来，不是按「哪条 API 最省事」来。

## 坑 11 — 界面上不显示路径 = 等于没做完

**现象**

用户看日志、滑到最底部才发现注入成功，然后还得自己猜文件在哪。

**根因**

结果面板放在日志区下面，且只显示包名、注入点、体积，没有路径。

**修法**

- 结果面板**置顶**（在日志之前）
- 完整路径用高亮框 + 等宽字体显示
- 紧跟「安装 / MT 定位 / 分享」三个按钮
- 日志折叠，默认收起

**教训**

> 对工具类 App，**「结果在哪」比「过程如何」重要**。
> 过程信息可以折叠，结果信息必须第一时间可见，并且要能一键跳到产物。

## 坑 12 — `getPackageInfo` 在 Android 11+ 需要 `<queries>`

**现象**

装了 MT 管理器，但 `isMtInstalled()` 一直返回 `false`。

**根因**

Android 11（API 30）引入**包可见性限制**：不声明的包，`getPackageInfo` 会抛 `NameNotFoundException`。

**修法**

```xml
<queries>
    <package android:name="bin.mt.plus" />
</queries>
```

**教训**

> 任何 `getPackageInfo` / `queryIntentActivities` 调用，在 targetSdk 30+ 都要配套 `<queries>`。
> 否则「探测某 App 是否安装」这类逻辑会**静默失效**，而且异常被 catch 后看起来像「没装」。

## 坑 13 — 测试断言写死 `classes.dex` 不成立

**现象**

```kotlin
assertEquals("应在 classes.dex 里", "classes.dex", r.dexName)
// ComparisonFailure: expected:<classes[].dex> but was:<classes[4].dex>
```

**根因**

`MainActivity` 实际被 AGP 分到 `classes4.dex`。dex 的切分随 AGP 版本、依赖数量、构建配置变化，**没有任何保证**。

**修法**

断言「非空」而不是断言具体值：

```kotlin
assertTrue("应记录命中的 dex 名", !r.dexName.isNullOrBlank())
```

**教训**

> 测试断言只应该钉住**契约**，不应该钉住**实现细节**。
> 「实现在哪个 dex」是 AGP 的自由，不是本工程的契约。

## 坑 14 — 配置混在主页面里就没法用

**现象**

第一版把配置的增删改查塞进主注入页的一张卡：不能改名、看不到内容、没有独立入口、和注入主线混在一起。

**根因**

把「管理」和「执行」放在同一屏。

**修法**

拆成侧边栏两个页面：

- **注入页**：只留一个配置选择器（下拉显示当前配置摘要）
- **配置页**：完整增删改查，列表 + 编辑器两种视图

**教训**

> **「管理」和「执行」是两种不同的心智模式**，混在一屏时两者都做不好。
> 执行页要窄而直，管理页可以宽而全。

## 坑 15 — 编辑配置时不保留原 dex 会丢文件

**现象**

（预防性设计，未发生）用户只改配置名，`dexSource` 为 null，dex 字段被写成 null。

**根因**

`upsert` 无脑用传入的 `dexSource` 覆盖 `dexPath`。

**修法**

```kotlin
val storedDex = when {
    dexSource != null -> 复制到 files/configs/<id>.dex
    keepExistingDexIfNull && existing?.dexPath != null -> existing.dexPath  // 保留
    else -> null
}
```

**教训**

> **部分更新语义**：编辑表单时，「用户没碰的字段」意味着「保持不变」，不是「清空」。

## 坑 16 — 注入载荷直接 `show()` 会抛 `BadTokenException`

**现象**

示例 payload 在 `onCreate` 注入点里直接弹 `AlertDialog`，App 崩：

```
WindowManager$BadTokenException: Unable to add window -- token null is not for an application
```

**根因**

注入点在 `onCreate` 的**第一条指令之前**，此时 Activity 的窗口 token 还没就绪。

**修法**

```java
new Handler(Looper.getMainLooper()).postDelayed(runnable, 800L);
```

post 到主线程消息队列，等 `onCreate` 返回、窗口就绪后再弹。

另外参数必须是 `Activity` 而不是 `Context`：`AlertDialog` 需要 Activity 的窗口 token，传 ApplicationContext 一样崩。

**教训**

> 注入点越早 ≠ 越好用。**「够早」和「环境就绪」是两个约束**，
> 大多数 UI 相关的载荷都需要延后到窗口就绪。

## 坑 17 — 二进制 AXML 的 UTF-8 字符串有双长度前缀

**现象**

（实现时注意到的细节）解析字符串池时字符串错位。

**根因**

`RES_STRING_POOL` 的 `flags & 0x100` 决定编码：

- **UTF-8**：`u16 字符长度` + `u8 字节长度` + 数据 + `\0`
- **UTF-16**：`u16 字符长度` + 数据 + `\0\0`

两个长度都可能占两字节（首字节高位为 1 表示后续还有一字节）。

**修法**

```kotlin
val b0 = buf.get(p).toInt() and 0xFF
p += if (b0 and 0x80 != 0) 2 else 1
val b1 = buf.get(p).toInt() and 0xFF
if (b1 and 0x80 != 0) {
    byteLen = ((b1 and 0x7F) shl 8) or (buf.get(p + 1).toInt() and 0xFF)
    p += 2
} else {
    byteLen = b1; p += 1
}
```

**教训**

> 二进制格式里的「长度」字段经常是变长的（protobuf varint、AXML 的这两个长度）。
> 按「固定 2 字节」读会静默错位，而且错位后读出来的字符串可能仍然「看起来像字符串」，很难发现。

## 坑 18 — `platforms;android-37` 这个包根本不存在

**现象**

CNB 云端打包连续三次失败，第一次「生成示例 payload dex」报
`缺少: /opt/android-sdk-linux/platforms/android-37/android.jar`，
补装之后「补齐 android-37 平台」stage 又报
`/opt/android-sdk-linux/cmdline-tools/latest/bin/sdkmanager: not found`。

**根因（三个独立的错，叠在一起才显得像「装不上」）**

1. **包名错**。Google 的 sdk repo 里没有 `platforms;android-37`。
   从 API 36 起平台改用「主版本.次版本」命名，包叫 `platforms;android-37.0`，
   装完的目录是 `platforms/android-37.0`。整数形态只保留到 `android-36`。
2. **sdkmanager 路径错**。镜像把 cmdline-tools 直接解压到 `$ANDROID_HOME` 根，
   可执行文件在 `$ANDROID_HOME/cmdline-tools/bin/sdkmanager`，**没有 `latest/` 这一层**。
3. **`build.sh` 只认整数目录**。它的探测是
   `case "$n" in *[!0-9]*) continue`，`37.0` 含点号所以被整段跳过 ——
   就算平台装好了也照样报「找不到 android.jar」。

而且 `sdkmanager` 对不存在的包**只打一句 Warning 然后 exit 0**，
所以「安装失败」不会在安装那一步暴露，要到下一步才炸。

**修法**

- 新增 `.cnb/scripts/ensure-sdk.sh`，逻辑收敛成一份，三个入口共用：
  - `compileSdk` 从 `app/build.gradle.kts` 读，不写死数字
  - 包名先 `sdkmanager --list` 校准，再从列表里挑（`android-37` → `android-37.0` → 前缀取最高非预览版）
  - sdkmanager 按 `latest/bin` → `cmdline-tools/bin` → `tools/bin` → `PATH` 逐个探测
  - 装完**自己复核** `android.jar` 和 `build-tools/*/d8` 是否真的在，不信 sdkmanager 的退出码
  - 只装缺的部分：全量重装会让 sdkmanager 把已存在的目录另存为 `android-37.0-2`
  - 顺带做 JDK 自检（`jvmToolchain(21)` 要求 ≥21，而 `:34.0.1` 镜像自带的是 JDK **17**）
- `tools/sample-payload/build.sh` 的版本探测改成按点分版本号数值排序，
  并跳过 `-beta1` / `-ext19` / `canary` 这类非稳定 base 平台。
- 流水线镜像从 `:34.0.1` 换 `:36.1.0`（后者自带 openjdk-21）。

**教训**

> 「包不存在」和「工具不在」在日志里长得几乎一样，都是一行失败。
> 判断这类问题的顺序应该是：**先确认工具能跑（绝对路径 + 版本号），再确认要的包在仓库列表里，
> 最后才相信安装结果** —— 因为很多包管理器的默认行为是「找不到也 exit 0」。
>
> 还有一条更通用的：**上游改了命名规则时，写死的字符串不会报错，只会静默不匹配。**
> 凡是「把外部资源名写进配置」的地方，都应该先能列出外部实际有什么。

## 坑 19 — 每个页面各自 `viewModel()`，三个页面变成三个世界

**现象**

新 UI 里「控制台 → 注入配置 → 运行」是同一件事的三个阶段。第一版三个页面都写
`vm: ConsoleViewModel = viewModel()`，结果：在配置页选好的配置，运行页读不到；
跑完回到控制台，锚点卡还显示「就绪」。

**根因**

`viewModel()` 默认以**当前的 `NavBackStackEntry`** 作为 `ViewModelStoreOwner`。
每个 `composable(route)` 都有自己的 `NavBackStackEntry`，于是每次调用都新建一份实例
——三份状态互不相通，且各自随页面销毁而丢。

**修法**

在 `AppRoot`（NavHost 之上）取一份，按参数往下传：

```kotlin
@Composable
fun AppRoot(console: ConsoleViewModel = viewModel()) { ... }
```

此时 owner 是 Activity，天然共享，且能扛住旋转。子页面的签名改成必填参数
（`vm: ConsoleViewModel`，不给默认值）——**默认值本身就是这个 bug 的入口**，
不给默认值，编译期就能发现谁在偷偷新建。

**教训**

> 跨页面的共享状态，`ViewModel` 的 owner 必须**高于**这些页面的共同祖先。
> 用 `viewModel()` 的默认参数写 Composable 很顺手，但顺手的那一下正好隐藏了作用域。
> 凡是「共享」的 VM，签名里就别留默认值。

## 坑 20 — 抽屉里 `popUpTo(start)` + 直接 `navigate` 混用，回退栈成环

**现象**

侧边栏三页时：从配置页点「去注入」，再从侧边栏点「配置」，「建完配置回不到注入页」。

**根因**

抽屉切换用的是

```kotlin
nav.navigate(dest.route) {
    popUpTo(AppDest.INJECT.route) { saveState = true }   // 把注入页当栈底
    launchSingleTop = true
    restoreState = true
}
```

而配置页里「去注入」是另一条路径：直接 `nav.navigate(INJECT)`。
两条路径互相插队，回退栈里会出现 `inject → config → inject → config`。
用户按返回时退到的是中间那层，看起来像「回不去」。

**修法**

把「平级切换」和「下钻」分开：

| 场景 | 做法 |
|---|---|
| 侧边栏四个平级入口 | `navigate { popUpTo(栈底) { saveState }; launchSingleTop; restoreState }` |
| 控制台 → 注入配置 / 运行 | 纯 `navigate`，返回用 `popBackStack(栈底, inclusive = false)` |
| 子页里跳去平级页 | 先 `popBackStack(栈底)` 再 `go(dest)` |

另外把「回到某一页」从「依赖回退栈里还剩下什么」改成**显式目标**
（`popBackStack(CONSOLE, inclusive = false)`）。栈里的历史不会总如你所愿。

**教训**

> 导航的两套机制（`popUpTo` 的栈维护 vs `navigate` 的入栈）不能随手混用。
> 混用的症状不是崩溃，而是「多点几下才回不去」——**这类 bug 只能靠把规则写下来避免**，
> 靠点测试永远覆盖不全。

## 坑 21 — native 的 `onCreate` 不能注入，直接报错等于把用户堵死

**现象**

加固壳或 `NativeActivity` 的 `onCreate` 是 `native` 方法（只有签名、没有字节码）。
旧实现走到 `DexCallInjector` 里返回 `Skipped("onCreate 是 native，无方法体可插")`，
用户在界面上只看到一行红字，不知道下一步该选哪个方法。

**根因**

把「不可插」当成错误上报，而不是当成**需要重新决策的输入**。

**修法**

`LifecyclePoints.resolve()` 里做降级，顺序是**时机接近度**：

```
onPostCreate(Bundle)  ← onCreate 返回后立刻执行，拿到同一份 savedInstanceState
onStart()             ← 同一帧内紧随其后
onResume()            ← 可交互时机
attachBaseContext()   ← 更早，但还没有 Activity 窗口，载荷要 Activity 参数的放最后
```

三条硬约束：

1. 只在**真的插不进去**时降级（`Status.NATIVE`），`MISSING` 不降级——类里没有就新建；
2. 替代点必须来自**同一个类的可用清单**（对 `Application` 不能推荐 `onPostCreate`）；
3. 原因必须写进 UI（`resolution.reason`），因为这是系统替用户做的决定。

**教训**

> 「不可用」的输入应当触发**自动重规划**，而不是中断流程。
> 但重规划必须**可见**——悄悄替你换掉一个方法，比报错更危险：
> 用户以为注入在 `onCreate`，实际在 `onPostCreate`，调试时会对不上号。
>
> 顺带一条领域知识：`onPostCreate` 是与 `onCreate` 语义最接近的可插点。
> 它在 `ActivityThread.callActivityOnPostCreate` 里被调用，参数就是 `onCreate` 收到的
> `savedInstanceState`，中间只隔着一次 `onStart` 的时机判断。

## 坑 22 — 进度条要「真」，日志飞滚也得是「真」的

**现象**

（预防性设计）上一版执行时只有一个转圈动画 + 日志一行行冒出来，
用户原话是「感觉它在跑，但我不知道跑到哪了」。

**根因**

流水线只吐「事件」，不吐「位置」。UI 拿不到总进度，只能自己编一个匀速填充。

**修法**

让流水线自己带坐标：

- 每个阶段有 **weight**（重打包 4、注入 3、定位 2.5…），`progressOf(stage, sub)`
  把「阶段 + 阶段内 0~1」折算成全局 0~1，阶段交界处不跳变；
- `ApkRepackager.repack()` 暴露 `onEntry(index, total, name)` 回调，
  重打包那几百个条目是日志快速刷屏的**真实来源**；
- 条目上千时按总量切成 ~60 段采样上报——全量上报会把日志刷成噪音，
  反而看不出「在动」。

单测 `LifecyclePointsTest.进度在整个流水线上单调不减` 钉住「不倒退、不越界、收在 1.0」。

**教训**

> 进度条的价值来自「它和实际工作成正比」。一旦为了好看而加速、平滑或补齐，
> 它就变成了装饰品 —— 而用户恰恰是用它来判断「卡住了没有」。
> 要让进度真实，就必须让**干活的代码自己上报进度**，而不是在 UI 层猜。

## 坑 23 — 换类名后沿用了「不属于这个类」的生命周期方法

**现象**

（由单测抓到，未流入使用）在 Activity 上选好 `onPostCreate`，再把类名改成一个
`Application` 子类（或反过来）。注入照常「成功」，但产物装上之后毫无效果。

**根因**

`targetMethod` 是用户的选择，换类时没人去校验它还成不成立。
`Application` 没有 `onPostCreate` —— `DexCallInjector` 会老老实实**新建**一个
`onPostCreate(Bundle)V`，还贴心地补上 `invoke-super`。可框架永远不会调用它。
这是最坏的一类失败：日志全绿、产物正常、行为为零。

**修法**

把「体系错配」交给 `LifecyclePoints.resolve()` 判，判据是两条同时成立：

1. 这个名字出现在**标准清单**里（`LifecyclePoints.ALL_STANDARD`）；
2. 但它不在**当前类**的清单里（`forSuperClass()` 给的那套）。

同时成立 → 换成当前类清单里的 `onCreate`，并把原因回传。
只满足第 1 条不满足第 2 条的反面情况是**用户自定义方法名**（`myForgeHook`），
那种一律保留 —— 他明确知道自己在干什么，系统不该替他改。

**教训**

> 「用户的选择」和「系统的约束」冲突时，先判断冲突是否**已经发生**，
> 而不是一上来就校验。这里真正的信号不是「方法名不在清单里」，
> 而是「方法名在**另一个体系**的清单里」—— 后者才说明用户是基于旧上下文做的选择。
>
> 还有一个更普遍的：**没有任何报错的失败最难查**。凡是「注入成功」这条路径，
> 都要问一句「它凭什么一定会被执行」。生命周期方法靠框架调，框架只认它认识的那几个名字。
