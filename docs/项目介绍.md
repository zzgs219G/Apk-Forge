# 项目介绍

## 一句话

把「往别人的 APK 里插一段代码」这件事，做成手机上点几下就能完成的流程。

## 与相关工程的关系

| 工程 | 形态 | 与本工程关系 |
|---|---|---|
| `artifact-pipeline` | 云端 GitHub Actions 流水线 | **同领域，不同形态**。它跑在 CI 上，用 apktool 解包 → 改 smali 文本 → 回编；本工程跑在手机上，用 dexlib2 直接改 dex 字节码 |
| `jian_box` | 云端 APK 加固客户端 | 借鉴它的**文件选择策略**（MT 优先 + 系统降级）与**页面信息结构**；未复制它的抽屉手势实现与 UI |
| `sx_rjk` | Android 工程 | 借鉴其**构建配置**（AGP/Kotlin 版本组合、Termux 加速参数） |

### 为什么不用 apktool 那套

artifact-pipeline 用 apktool 是合理的：它在服务器上跑，有充足内存和 CPU，需要处理几十年积累的畸形 APK。

本工程在手机上，所以选了 dexlib2 直改：

| | apktool（文本往返） | dexlib2（字节码直改） |
|---|---|---|
| 速度 | 大包 10~50 倍慢 | 30MB 包秒级 |
| 保真 | 不保真：debug_info 膨胀（实测 63KB→1.86MB）、dex 版本头被写回 035（导致 Compose 包 ICCE 闪退） | 只改目标方法，其余原样 |
| Manifest | 有「文本 Manifest 装回包产出灰包」的坑 | 全程二进制，不碰 |

artifact-pipeline 为这两个保真问题各写了一个补丁脚本（`--no-debug-info`、`patch-dex-version.py`）。dexlib2 路线从根上没有这两个问题。

### 但 dexlib2 也不是终点：为什么又写了一层增量引擎

dexlib2 的 `DexPool.writeTo` 会**重新 interning 整个池**——
8.5 万个字符串重新 MUTF-8 编码、6 万个方法重新序列化。
实测 28.5MB 的 dex **即使什么都不改**也要 9~18 秒。

而实际需要新增的只有 2~5 个池条目。于是有了 `core/dex/patch/` 这一层：

| | `DexCallInjector`（全量） | `PoolInjector`（增量） |
|---|---|---|
| 池 | 全部重排、重新 interning | 只插新条目，旧索引尽量不动 |
| 指令 | 全部重新编码 | **不重编码**，只回填真正变了的索引（约 8.5%） |
| 耗时（28.5MB） | 9~18 秒 | **约 1.1 秒** |
| 适用性 | 任何形态 | 新建方法 / 替换方法体 / 带 try 的会回退 |

代价是**必须自己保证 dex 布局合法**（ART 的四条约束，见 `AGENTS.md` §10）。
这一层前后修了 9 个真 bug，全是「结构非法」或「内容被改错」，
而 ART 的格式校验器只能查出前一类。

两条路径不是替换关系：增量是**快路径**，全量是**正确性保底**。

### 为什么批量与控制台是两个 VM

「一个包，反复调参再跑」和「一次挑一批，跑完就走」是两种不同的作息。
塞进同一个 VM 后，「当前任务是哪个包」「这行日志是谁的」都会变得含混。
拆开之后，控制台仍是单任务的权威，批量自己管队列——它们的界面也因此可以完全不同。

### 界面只有三级

旧版把配置、选包、类名、方法、结果、日志全摊在一屏，每块都在抢注意力，
用户第一眼的问题是「我该点哪」。现在：

| 层 | 内容 | 心智 |
|---|---|---|
| 锚点 | 一张卡，一颗按钮 | 「现在该干什么」只有一个答案 |
| 记录 | 跑过的任务列表 | 「上次怎么弄的」不用重来 |
| 子页 | 注入配置 / 运行 | 决策与执行分开，各自专注 |

配置管理、签名、关于退到侧边栏——它们是**平行的事**，不该和主流程抢位置。

### 分层原则

**`inject/` 里的核心逻辑刻意不依赖 Android API**（除了 `Context` 相关的 `OutputStore` / `FilePicker` / `ConfigStore`）。

理由：这样能在 Termux 的 JVM 上直接用 `junit` 跑真实 APK 的端到端验证。二进制改写这种代码，靠点 UI 来验证是不负责任的——出错了只会看到「闪退」，不知道错在哪。

当前 `app/src/test/` 里的断言全部基于真实 APK（默认取本工程自己的 debug 产物）。
不写具体条数——数字每加一条测试就过期一次，而「哪些契约被钉住了」才是要传达的信息。
准确条数以 `sh gradlew :app:testDebugUnitTest` 的输出为准：

- `InjectEndToEndTest` — Manifest 逐字节不变、dex 可解析、指令在头部、
  新建方法补 super、多行顺序、生命周期替代点也补 super、**重打包逐条目回调完整**、
  **替换方法体后只剩两条指令**、**额外资产进包且同名替换**
- `PipelineEndToEndTest` — 整条流水线跑通、产物只多一个 `classesN.dex`、
  进度单调且**阶段序号不许倒退**、调用行语法错误与类名找不到时给可执行的下一步
- `RepackArtifactTest` — **dex 版本头不被改写**、**STORED 条目保持原有对齐**、
  `Stats` 如实报告对齐与源包签名状态
- `InjectionModeTest` — 每种模式的落点：单次不扩点、每次进入去重不重复、
  多点排除 native、Application 不拿 Activity 的点、替换标记唯一、沿用 native 降级结论
- `LifecyclePointsTest` — native 降级顺序、不误改用户选择、全 native 时如实报错、
  替代点必须来自本类清单、换类后不沿用别体系的方法名、自定义方法名不被改、
  进度单调且收在 1.0、清单签名可被解析器认下
- `ClassInspectorTest` — 方法探测准确性、生命周期点签名一致性
- `PluginPayloadTest` — 调用行与载荷 dex 的方法逐字一致且 `public static`、
  dex 魔数与体积上限、资产路径常量对齐、JSONC 去注释不吞字符串里的斜杠
- `SamplePayloadTest` — 示例 dex 与 UI 预填调用行一致

## 关键设计决定

### 1. 注入点用「用户粘贴 smali 行」，不用三段式表单

用户真实操作是：MT 反编译 → 看到 `invoke-static {p0}, Lcom/foo/Bar;->init(...)V` → 复制。让他拆成「类名 / 方法名 / 签名」三个框是逆人性的。

`SmaliCallParser` 直接解析整行，支持 `invoke-static/virtual/direct/super/interface`、`/range` 形态、`#` 注释、数组类型。

### 2. 寄存器宽度自动降级

`invoke-*` 的 35c 格式寄存器列表只有 4 bit（v0–v15）。用户复制的那行来自**别的方法**，寄存器布局与目标方法不同。

所以不能照抄形态：按实际物理寄存器号判断，超 v15 或超过 5 个就换 `/range`（3rc，16 bit）。寄存器不连续时直接报错，不静默产出非法 dex。

### 3. 方法不存在时新建，且必须补父类调用

`onCreate` 覆写缺失是合法且常见的。新建方法体：

```
invoke-super {p0, p1}, Lcom/foo/Base;->onCreate(Landroid/os/Bundle;)V
invoke-static {p0}, Lcom/payload/Demo;->inject(Landroid/app/Activity;)V
return-void
```

**父类调用是关键**：不调 `super.onCreate` 会让 Activity 生命周期状态机断裂。

判定依据是「父类是否声明了同名同签名方法」，不是硬编码方法名白名单——白名单会漏掉 `onNewIntent`、`onPostCreate`。

### 4. 配置 = 调用 + dex + 模式，作为一个持久化单元

用户攒的是「一套注入方案」，不是「一次注入」。`ConfigStore` 把它们绑在一起存，dex 复制进 `files/configs/<id>.dex`（`cacheDir` 里的会被系统清掉）。

**注入点不在配置里**。配置只管「注入什么」（调用行、载荷、模式、附带资产），
「注到哪个类的哪个方法」是包自己的属性：每个包的 Lifecycle 方法集合都不一样，
跟着配置走会漂到不存在的目标上（见 `踩坑记录` 坑 23）。

不用 Room：只需「存几条、列出来、改名、删掉」，`org.json` 是平台内置，零依赖零注解处理器。

### 4.5 注入模式与落点，判定只写一遍

四种模式（单次 / 每次进入 / 多点 / 替换方法体）全部落进 `InjectionPlanner` —— 一个纯 JVM
对象，入参是「当前类的生命周期清单 + 类里真实存在的方法 + 用户想要的点」。

这样做的理由不是「少写代码」，而是：**这四种模式的错法全都表现为「注入成功但行为为零」**。
日志全绿、产物正常、效果没有，没有任何报错。只有把判定收成一处、能被单测钉住，
才能在改动时及时发现「`Application` 被铺上了 `onPostCreate`」这类错位。

### 4.6 弹窗载荷为什么独立成 `payload/`

它不是 App 的一部分，而是要**被注入进别人 App 的东西**。因此它的约束比 App 严得多：

- 零第三方依赖（只用 `android.app.AlertDialog` + `org.json`），体积约 21KB；
- 没有网络代码：**配置烘焙在 dex 里**，行为完全可解释、可离线验证；
- **不碰宿主的任何资产**：产物只多一个 `classesN.dex`。上一版往 `assets/` 写 json，
  等于多一条会断的通道（资产没写进去 = 注入成功但不弹窗，且不报错）；
- 类名与方法名是**契约**：调用行里硬编码，所以构建脚本刻意不开 R8/desugar 的改名；
- min-api 是 21，构建期用 `android-21/android.jar` 再编一遍做硬门禁——
  `d8 --min-api` 只影响 desugar 策略，挡不住「调用了设备上不存在的 API」；
- 契约由 `PluginPayloadTest` 钉住（方法必须 `public static`、占位符全 dex 唯一、
  烘焙往返逐字一致、7.0 老配置能归一化）。

它的构建（`javac + d8`）与 App 的 Gradle 构建完全解耦，因为两边要的确定性不一样：
App 要快，载荷要「产出逐字节可复现」。

配置的落法值得单独说一句：**烘焙进 dex，而不是作为资产文件跟着跑**。
实现是 `core/dex/PayloadBaker` —— 把 `PayloadConfig.baked()` 的方法体换成
`const-string + return-object`，再用 `DexPool` 整体重写。唯一性是硬前提：
占位符必须由方法返回（`static final` 会被 javac 内联成多份），
构建期数字节、单测再钉一遍。代价是改文案要重新导出 + 重新注入，这就是取舍本身。

### 5. 产物写 Download 而不是 getExternalFilesDir

`/sdcard/Android/data/<pkg>/files/` 在 Android 11+ 的文件管理器里**看不到**，MT 也要单独授权。用户注入完找不到文件等于白做。

改用 MediaStore 插入 Downloads 集合：Android 10+ 免权限，落盘位置就是用户熟悉的 `Download/ApkForge/`。

## UI 取向

不是「学习项目演示」风格，是「干活工具」风格。三条自检标准：

**1. 主操作的位置固定且够得着。** 全 App 只有一个主按钮，做成贴底的常驻栏，
而不是长在卡片里跟着内容走。滚动到哪它都在，单手拇指也能按到。

**2. 同一时刻只有一个视觉重心。** 运行中是进度 + 单行实时日志；完成后进度区整块撤掉，
由结果卡接管。两张卡说同一件事（「已完成」），用户会先去读哪个？

**3. 该完整的地方不许省略。** 日志、调用行、产物路径的尾部就是唯一标识
（方法名、签名、文件名）。这些东西换行，不截断，并且必须有复制入口——
这份工具的日志天然会被贴进对话里求助。

关于动画：只保留一套六边形（真实 SVG path 描边生长）。上一版做了「环形 / 六边形」
可选，代码成本只有一个 `when`，但**风格选择本身没有用户价值**——没人会因为能选动画
而更想用这个工具。完成动画收进结果卡当卡头图标，不再覆盖内容（那是「遮挡」的观感来源）。

关于暗色：固定深色，不跟随系统。理由不是审美，是这条链路上只要有一处配色写死，
全链路就必须一起跟随，否则会在某个分支上撞车——撞车的表现不是「颜色难看」，
而是「某段文字彻底看不见」（见 `踩坑记录` 坑 24）。
